## 1. 계기 — 거래일 누락 사고

이 저장소는 **quant 의 `src/live/` 5,958줄을 폐기하고 다시 만든 것**입니다. 그 결정의 계기는
2026-08-26~29 에 일어난 사고입니다.

quant 의 `daily_run` 워크플로 cron(`27 22 * * 1-5` = 07:27 KST)이 GitHub 측 사유로 심하게
지연되면서, **2026-08-27 거래일이 어느 실행에서도 처리되지 않았습니다.**

| 예정(UTC) | 실제 실행(UTC) | 지연 | 실행 시점 NY 날짜 | 결과 |
| --- | --- | --- | --- | --- |
| 08-25 22:27 | 08-25 22:51 | 25분 | 08-25 (화) | 성공 |
| 08-26 22:27 | 08-27 03:24 | 4시간 58분 | 08-26 23:24 (수) | 성공 (37분 차로 세이프) |
| 08-27 22:27 | 08-28 06:11 | **7시간 45분** | **08-28 02:11 (금)** | 실패 |
| 08-28 22:27 | 08-29 03:45 | 5시간 19분 | 08-28 23:45 (금) | 실패 |

**인과**: 워크플로가 `TZ: America/New_York` 을 설정하고 `cli.py` 가 `date.today()` 로 처리 대상
거래일을 정했습니다. 실행이 자정을 넘기면 대상 날짜가 하루 밀리고, 그 결과 08-27 은 처리 기회를
잃었습니다. 이후 `validate_date_gap` 이 CSV 마지막(08-26)과 대상일(08-28) 사이의 누락을 감지해
중단시켰습니다. 「보간 금지 / 자동 복구 금지」 원칙상 **자동으로는 영원히 풀리지 않는 상태**였습니다.

**결정적 관찰**: job 실행 자체는 **55초**로 정상이었고, 큐 대기(created_at → started_at)는 **3초**였습니다.
즉 깨진 것은 GitHub Actions 의 **실행 능력이 아니라 cron 발화 시각**이며, 그것을 치명적으로 만든 것은
**매일 갱신되는 누적 상태**였습니다.

> 이 두 문장이 이 저장소 설계의 전부입니다. **트리거 정시성은 남의 손에 있고, 상태는 내 손에 있습니다.**
> 그래서 상태를 없앴고, 트리거는 §6 처럼 우회했습니다.

## 2. 실측 — 발송 시각 분포

텔레그램 로그 3개월치(2026-06-02 ~ 08-27, 정상 리포트 **61건**)를 파싱한 결과입니다.
cron 은 이 기간 내내 07:27 KST 로 동일했습니다.

| 통계 | 발송 시각(KST) | 예정 대비 지연 |
| --- | --- | --- |
| 최소 | 07:46 | 19분 |
| **중앙값** | **08:31** | **64분** |
| 75% | 08:48 | 81분 |
| 최대 | 12:25 | 4시간 58분 |

월별로는 6월 중앙 1시간 23분 → 7월 1시간 1분 → 8월 37분으로 개선 추세였습니다.
**평상시에도 1시간 안팎 지연되는 것이 정상 상태였다**는 점이 중요합니다.
최근 며칠만 보면 20분대로 보여 오판하기 쉽습니다.

판정 시각별로 "그때까지 알림이 안 온 정상 건"의 비율:

| 판단 시각 | 아직 안 온 건 | 비율 |
| --- | --- | --- |
| 08:30 | 31/61 | 50.8% |
| 08:45 | 16/61 | 26.2% |
| 09:00 | 6/61 | 9.8% |
| 13:00 | 0/61 | **0.0%** |

> **이 수치는 다시 잴 수 없습니다.** 텔레그램 로그를 파싱해 얻은 값이고, 그 로그가 사라지면
> 재현할 방법이 없습니다. **장중 알림 설계(§6)의 유일한 정량 근거이므로 지우지 마세요.**

## 3. 근본 결정 — 상태를 갖지 않는다

### 3.1 무엇을 없앴나

quant `src/live/` 는 model/actual equity 원장, drift, 미입력 체결 리마인더, 시그널, 리밸런싱,
MA 근접도를 모두 다뤘습니다. 이 중 **누적 상태를 요구하는 것을 전부 걷어냈습니다.**

| 폐기 대상 | 규모 | 사유 |
| --- | --- | --- |
| `rtdb_gateway.py` | 685줄 | 앱 폐기로 RTDB 불필요 |
| `chart_data.py` | 607줄 | 차트 폐기 |
| `daily_runner.py` | 551줄 대부분 | 포트폴리오 엔진 호출 불필요 |
| `state.py` | 499줄 | 보유수량·평단 원장 불필요 |
| `storage_gateway.py` · `history.py` · `drift.py` · `balance_adjust.py` · `buffer_serializer.py` | 980+줄 | 상태가 없어져 전부 불필요 |
| `data_validator.py` 대부분 | 152줄 | `validate_date_gap` 은 **개념 자체가 사라짐** |
| Firebase 프로젝트 | — | FCM · RTDB · GCS 모두 미사용 |
| `keepalive.yml` | — | 60일 무활동 정지는 `schedule` 워크플로 전용. 이 저장소는 쓰지 않음 (§6.3) |

**이 결정이 사고의 근원을 제거합니다.** 남은 지표는 종가와 이동평균만으로 계산되며 누적 상태가
없습니다. 따라서 `live_state.json`, GCS 정본, `validate_date_gap` 이 모두 불필요해지고,
**실행이 하루 누락되거나 8시간 지연돼도 피해가 없습니다.** 다음 날 오면 그만입니다.

### 3.2 계산을 이 저장소가 직접 한다

**quant 에 의존하지 않습니다.** SMA 전환(quant 부록 G) 덕분에 가능해졌습니다.

EMA 는 재귀식이라 quant 와 동일한 값을 내려면 전체 히스토리가 필요했지만, **SMA 는 최근 1년치만
받아도 누가 계산하든 같은 값**이 나옵니다. 티커 목록과 MA 기간(200)만 알면 `rolling(200).mean()`
한 줄로 끝납니다.

같은 원리가 역방향 규칙에도 적용됩니다. 순위 등락률은 전체 히스토리가 필요하지만, **그 값만
넘겨받으면** 신호 가격은 `전일 종가 × (1 ± 순위 등락률)` 한 줄로 나옵니다 (§5.2).

### 3.3 발송은 텔레그램만

FCM 과 Android 앱을 폐기했습니다. `firebase_admin` 의존성, 서비스 계정 JSON,
`GOOGLE_APPLICATION_CREDENTIALS`, `secrets/` 생성 스텝이 전부 사라집니다.

### 3.4 별도 저장소로 분리한다

분리의 본질적 이유는 **알림 프로젝트의 값어치가 발송 자체가 아니라 여러 프로젝트의 스케줄과
감시를 한곳에 모으는 것**이라는 데 있습니다. quant 와 verify-lab 두 곳이 신호를 냅니다.

**퍼블릭으로 둡니다** (2026-09-05 결정). 처음에는 프라이빗을 전제했으나, 그 전제가 기대던
두 근거가 **모두 성립하지 않았습니다.**

| 프라이빗을 택했던 근거 | 실제 |
| --- | --- |
| 60일 무활동 자동 정지를 피한다 | **`schedule` 워크플로 전용 규칙**입니다. 이 저장소는 `workflow_dispatch` 만 쓰므로 대상이 아닙니다 (§6.3) |
| Actions 무료 분수(월 2,000분) | 퍼블릭은 표준 러너가 **무료 무제한**입니다. 제약 자체가 사라집니다 |

**감수하는 것은 `state/positions.toml` 의 공개입니다.** 보유 종목과 수량이 드러나고,
현재가를 곱하면 자산 규모가 계산되며, 커밋 히스토리는 **매매 시점과 수량 변화까지** 보여줍니다.
사용자가 이를 알고 감수하기로 결정했습니다 — **되돌릴 수 없다는 점도 포함해서입니다.**
퍼블릭 저장소는 fork·클론·아카이빙이 존재해 나중에 프라이빗으로 바꿔도 회수되지 않습니다.

시크릿은 공개 여부와 무관하게 GitHub Secrets 에 둡니다. 특히 `ECOS_API_KEY` 는 인증키가
URL 경로에 들어가므로 **로그와 예외 메시지 양쪽에서 마스킹**합니다 —
퍼블릭 저장소는 **Actions 실행 로그도 함께 공개**되기 때문입니다.

| 매매법 | 정본 | 알림 |

| Q-2-2XS 포트폴리오 | quant `portfolio_configs.py` | 1 |

**옵션 만기일은 알림을 만들지 않습니다.** 규칙 문서 §1.5 가 "연 2회뿐이라 기대 이익 대비 시스템
비용이 맞지 않는다"로 결정했고, 그 결정을 유지합니다.

### 4.2 알림 1 이 두 가지를 겸하는 이유

MA 근접도(전략이 정한 티커)와 보유 현황(사람이 적은 종목)은 **다를 수 있습니다.** 그래서 한
알림 안에서도 블록을 나눕니다. 합친 이유는 실행 시각이 같고(미국 종가 확정 후), 읽는 사람도
같은 아침에 한 번 보기 때문입니다.

**비중을 내려면 현재가가 필요합니다.** 평가액을 표시하지 않을 뿐 계산은 합니다 —
수량만으로 비중을 내면 주당 가격이 달라 뜻 없는 숫자가 나옵니다.

### 4.3 알림 2b 는 집행이 지난 신호입니다

미국 마감 후에 판정하므로 **종가가 이미 확정된 뒤**입니다. 그 신호로는 살 수 없습니다.

규칙 §3 결정 ④ 가 익일 시가 집행을 기각했고(갭이 수익의 2/3 를 가져감 — KODEX 기준
+57.84% → +19.88%), 새벽 집행(한국시간 5시 / 6시)은 사용자 판단으로 하지 않기로 했습니다.
**따라서 이 알림은 정보로만 남습니다.** 그 사실을 알고 받는 것이 전제입니다.

### 4.4 알림 3 이 주간 요약을 겸하는 이유

역방향은 **연 5~8회만 울립니다.** 몇 달을 조용할 수 있고, 그러면 "신호가 없는 것"과
"시스템이 죽은 것"이 구분되지 않습니다. 월요일 알림에 지난주 역방향 요약을 붙이면
**살아 있다는 것과 실제로 신호가 없었다는 것이 함께 확인**됩니다.

지난주 요약은 **방향별 양끝**(가장 오른 날 · 가장 내린 날)을 냅니다. 절대값 하나로 합치지 않는
이유는 순위 등락률이 방향별로 따로 매겨지기 때문입니다 — 규칙 문서가 절대값 기준을 명시적으로
배제했습니다: "절대값으로 바꾸면 신호가 절반이 되고 한쪽 방향이 구조적으로 묻힌다."

#### 알림 2a · `reverse_rank_kr`

상태 어휘는 **`근접` · `도달`** 둘입니다. 장중 판정이라 확정이 아니어서 「발생」을 쓰지 않습니다.

```
신호   105,200원   -6.31%
```

헤더만 바뀌는 변형:

```
[역방향] KODEX 200 · 폭락 도달   09-04 (금) 14:30
[역방향] KODEX 200 · 폭등 근접   09-04 (금) 12:00
```

양쪽 다 여유 1%p 밖이면 **아무것도 보내지 않습니다** (§4 표의 「침묵」).

```
종가   $619.50   +7.80%
```

```
    폭등   1위 +16.84%     20위  +7.42%     지난주 최고  +3.25%  09-02 (수)
    폭락   1위 -11.98%     20위  -6.87%     지난주 최저  -0.88%  09-01 (화)

점검
  지난주   08-31 (월) ~ 09-04 (금)
  버퍼존 5/5 · 역방향 KR 10/10 · US 5/5
```

**환율 옆의 날짜는 그 값의 기준일입니다.** 월요일 아침에 받는 값은 지난 금요일 종가라,
기준일이 없으면 언제 값인지 읽는 사람이 추론해야 합니다. 휴장이 꼈으면 더 예전 값입니다.

**지난주 역방향은 방향별 양끝입니다** — 가장 오른 날 하나, 가장 내린 날 하나. 절대값으로
합쳐 하나만 내지 않습니다. 순위가 방향별로 매겨지므로 그래야 위의 `1위`·`20위` 줄과 짝이 맞습니다 (§4.4).

지난주에 신호가 있었으면 **해당 방향 줄만** 바뀝니다.

```
    폭락   1위 -12.46%     20위  -6.31%     지난주 신호  -6.48%  09-02 (수)
```

**`1위` 를 표시하므로 `state/reverse_rank.toml` 에 1위 등락률도 담습니다.** 정본 §1.5 의
「소비하는 쪽에 넘기는 것」은 20위만 넘기지만, 이 알림이 1위를 함께 읽습니다. 갱신 주기는
20위와 같아(연 6~7회) 새 부담이 없습니다.

#### 실패 알림

```
[QBT · 실패] buffer_zone   09-04 (금) 07:31

RuntimeError: yfinance 조회 실패 — QQQ
```

**제목과 예외 메시지뿐입니다.** 「재시도하지 않습니다」 같은 안내를 붙이지 않습니다 —
재시도가 없다는 것은 이미 설계이고(§7.4), 매번 읽히는 문구가 아닙니다.

#### 백분위를 내지 않습니다 (2026-09-05 결정)

정본 `reference/원달러_백분위_알림.md` §1.2 는 **백분위 · 평균대비 · 범위** 셋을 정의하지만,
이 알림은 **평균대비만** 냅니다.

두 지표는 §1.2 가 밝힌 대로 **같은 방향을 가리킵니다** — 백분위가 낮을수록, 평균대비가
음수일수록 지금이 쌉니다. 같은 것을 두 번 말하므로 하나면 충분하고, 평균대비 쪽이
「얼마나」까지 알려줍니다. 백분위 1 과 3 의 차이는 읽어도 모르지만 `-5.3%` 와 `-1.3%` 는
바로 읽힙니다.

**정본과 어긋난 상태입니다.** verify-lab 정본은 여전히 백분위를 포함하며 `reference/`
스냅샷도 그대로 둡니다 — 스냅샷은 고치지 않는 것이 규칙입니다. 정본을 언젠가 맞출지는
verify-lab 쪽 판단입니다.

## 5. 저장하는 것과 저장하지 않는 것

### 5.1 두 종류의 상태를 구분한다

§3 이 없앤 것은 **프로그램이 매 실행마다 갱신하는 누적 상태**이고, 이 저장소가 두는 것은
**사람이 가끔 손으로 고치는 정적 상태**입니다. 성질이 다릅니다.

| | 자동 누적 상태 (폐기) | 사람이 쓰는 파일 (도입) |
| --- | --- | --- |
| 예 | `live_state.json` · 정본 CSV · 체결 원장 | `positions.toml` · `reverse_rank.toml` |
| 갱신 주체 | 매 실행마다 프로그램이 | 사람이, 바뀔 때만 |
| 하루 걸렀을 때 | **영구 손상** (§1 사고) | 아무 일도 없다 |
| 공백 검증 | 필요 (`validate_date_gap`) | 개념 자체가 없다 |
| 낡았을 때 | 실행이 막힌다 | 알림이 느슨해질 뿐 |

**git 추적 텍스트 파일**이면 충분합니다. 사람이 편집하고 커밋하면 다음 실행이 읽습니다.
DB 도 클라우드 저장소도 필요 없습니다 — **매일 갱신이 없어 DB 가 풀 문제가 없습니다.**
커밋은 매매했을 때만 생기고, 동시 쓰기도 트랜잭션도 없습니다 (§8).

### 5.2 두는 파일

| 파일 | 담는 것 | 갱신 빈도 |
| --- | --- | --- |
| `state/positions.toml` | 보유 종목 · 수량 | 매매할 때 |
| `state/reverse_rank.toml` | 폭등·폭락 순위 등락률 · 기준일 · 데이터 기간 | 연 6~7회 |

**형식은 TOML 입니다.** `tomllib` 이 파이썬 3.11+ 표준이라 **새 의존성이 없고**, `state/` 는
프로그램이 **읽기만** 하므로 `tomllib` 이 읽기 전용이라는 점이 제약이 되지 않습니다.
YAML 을 쓰지 않은 이유는 §8 에 있습니다.

**값은 비율로 적습니다** (`0.0610` = +6.10%). `.claude/rules/python.md` 의 「모든 비율은 0~1」을
파일까지 관철해, 읽는 코드가 단위를 환산하지 않습니다.

**`reverse_rank.toml` 에 전일 종가를 넣지 않습니다.** 규칙 문서 §1.5 가 지목한 대로입니다 —
"티커와 20위 등락률 두 개면 충분하다. 전일 종가를 넣으면 매일 갱신해야 하고, 그 순간
「연 6~7회 갱신」이라는 성질이 사라진다."

**낡아도 안전한 방향으로 틀립니다.** 새 극단이 들어오면 순위 값은 더 극단적이 되므로,
낡은 값은 임계가 **느슨한** 쪽입니다. 거짓 알림이 늘 뿐 진짜 신호는 놓치지 않습니다.

**파일이 없을 때의 동작은 둘로 갈립니다.**

| 파일 | 없거나 비어 있으면 |
| --- | --- |
| `positions.toml` | **보유 블록만 비우고 알림은 발송**합니다 (§4.5) |
| `reverse_rank.toml` | **실패 알림을 보냅니다** — 신호 가격을 만들 재료가 없어 판정 자체가 불가능합니다 |

역방향은 신호가 멀면 침묵하므로, **재료가 없어 조용한 것을 그냥 두면 「신호가 없어서 조용한 것」과
구분되지 않습니다.** §7.3 이 점검 줄을 둔 것과 같은 문제입니다 — 조용한 것과 죽은 것을 가릅니다.

참고 실측 (2026-08 기준):

| 대상 | 폭등 1위 | 폭등 20위 | 폭락 1위 | 폭락 20위 |
| --- | --- | --- | --- | --- |
| KODEX 200 | +24.17% (2026-07-31) | **+6.10%** | −12.46% (2026-03-04) | **−6.31%** |
| QQQ | +16.84% (2001-01-03) | **+7.42%** | −11.98% (2020-03-16) | **−6.87%** |

데이터 기간: KODEX 200 2002-10-15 ~ 2026-08-26 (5,890 거래일) · QQQ 1999-03-11 ~ 2026-08-25 (6,907 거래일).
**시세를 재수집하면 이 값이 바뀝니다.**

### 5.3 두지 않기로 한 것

나중에 "왜 안 넣었지"를 반복하지 않기 위해 적어 둡니다.

| 항목 | 왜 |
| --- | --- |
| **역방향 진행 포지션** | 청산 추적을 하지 않기로 했습니다. 알림은 **그날 신호 발생 여부만** 냅니다 |
| **평균단가 · 손익** | 보유 알림이 **보유량과 비중만** 냅니다. 평단은 비중 계산에 쓰이지 않습니다 |
| **달러 매수 기록** | 원달러 규칙 §1.5 가 "지금은 달러 보유가 0이라 입력할 내역이 없다"고 적어두었습니다. 알림 셋 중 어느 것도 읽지 않습니다 |
| **알림 발송 이력** | Actions 실행 이력이 이미 그 역할을 합니다 (§7) |
| **시세 CSV 정본** | 매 실행마다 필요한 만큼 받습니다. 정본을 두는 순간 거래일 공백 검증이 따라옵니다 |

### 5.4 데이터는 알림마다 따로 받는다

세 알림이 **서로 다른 시각에** 돌기 때문에 공유할 시점이 애초에 없습니다.
겹치는 것은 QQQ 전일 종가 하나뿐인데, 이걸 공유하려면 세 가지가 따라옵니다.

- **결합이 생깁니다** — 아침 실행이 실패하면 낮 알림도 못 돕니다
- **"언제 받았나 · 낡았나" 판정이 따라옵니다** — 캐시는 상태이고, 상태는 검증을 부릅니다
- **아낀 것이 거의 없습니다** — 종가 한 개를 아끼려고 위 둘을 짊어집니다

**대신 조회·검증 코드는 `src/notify/data/` 한 모듈에 모읍니다.** 데이터를 공유하는 것이 아니라
**같은 데이터를 다르게 읽는 코드가 생기는 것을 막는 것**이 목적입니다.

## 6. 스케줄과 정시성

### 6.1 문제 — schedule 이벤트는 밀린다

§1·§2 가 보여준 대로 GitHub 의 `schedule` 이벤트는 큐에서 best-effort 로 처리되어
중앙값 64분 지연됩니다. 장중 알림에는 치명적입니다 — **14:30 판정이 64분 밀리면 15:34 도착,
장이 끝난 뒤**입니다. 역방향 규칙 §1.5 도 "정시 실행이 보장되지 않는 스케줄러는 마감 1시간 전
알림에 쓸 수 없다"고 적었습니다.

### 6.2 해법 — 외부 스케줄러가 workflow_dispatch 를 부른다

밀리는 것은 **`schedule` 이벤트 하나**입니다. **`workflow_dispatch` 는 거의 즉시** 집힙니다.

```
cron-job.org  ──HTTPS──▶  GitHub API                      ──▶  Actions 실행
 (12:00 정각)              POST .../workflow_dispatch            (즉시 시작, ~55초)
                           Authorization: Bearer <PAT>
```

외부 스케줄러는 **"버튼을 대신 눌러주는 역할"만** 합니다. 계산과 발송은 전부 Actions 안에서 돕니다.
§1 에서 job 자체는 55초로 정상이었으므로, **트리거만 제때 오면 실행은 즉시 됩니다.**

**cron-job.org 를 씁니다.** 무료이고 잡 개수 제한이 없으며(fair use) 코드가 없습니다.
Cloudflare Workers Cron 은 정시성이 조금 더 좋지만(지터 수 초) Worker 배포와 시크릿 관리가
늘어나는데, 분 단위 호출과의 차이는 장중 알림에서 의미가 없습니다.

**감수하는 것**: GitHub 토큰이 외부 서비스에 놓입니다. **fine-grained PAT 로 이 저장소의
Actions 실행 권한만** 부여해 노출 범위를 좁힙니다 — 유출돼도 이 저장소의 워크플로를 돌리는 것
외에는 할 수 있는 것이 없습니다.

### 6.3 schedule 을 백업으로 두지 않는다

둘을 함께 두면 cron-job.org 가 dispatch 하고 schedule 이 나중에 또 발화해 **같은 알림이 두 번**
갑니다. 막으려면 "오늘 이미 성공한 실행이 있나"를 조회하는 로직이 워크플로마다 붙습니다.

**얻는 것 대비 과합니다.** 트리거가 죽어도 감지 경로가 셋 있고(§7), 수동 실행 버튼이 항상
있습니다. 중복 방지 로직이 통째로 사라집니다.

### 6.4 cron 잡 목록

| 잡 | 시각 (KST) |
| --- | --- |
| `buffer_zone` | 매 거래일 아침 |
| `reverse_rank_us` | 매 거래일 아침 |
| `reverse_rank_kr` | 평일 12:00 |
| `reverse_rank_kr` | 평일 14:30 |
| `usdkrw` | 월요일 아침 |

**cron 은 요일만 알고 휴장을 모릅니다.** 휴장일 판정은 워크플로 안에서 하고, 휴장이면
조용히 종료합니다.

## 7. 실패와 중복

### 7.1 중복 — 발생 경로가 없다

| 경로 | 상태 |
| --- | --- |
| cron-job.org + schedule 동시 발화 | **schedule 을 두지 않아 해당 없음** (§6.3) |
| cron-job.org 자체 재시도 | 실패 시에만 재호출. 성공 응답이면 재시도 없음 |
| 사용자 수동 실행이 자동과 겹침 | 발생 가능하지만 **의도된 행위**입니다. 막지 않습니다 |
| 같은 워크플로 동시 실행 | `concurrency` 그룹으로 워크플로당 1개 |

### 7.2 실패 — 층위별 감지

| 무엇이 깨졌나 | 어떻게 알아차리나 | 무엇을 하나 |
| --- | --- | --- |
| 알림 내부 오류 | `if: failure()` → **텔레그램 실패 알림** | 재시도 없음. 원인 확인 후 수동 실행 |
| cron-job.org 가 못 부름 | cron-job.org **실패 알림 메일** | 수동 `Run workflow` |
| 워크플로가 아예 안 돎 | **알림 1 이 안 옴** (매일 오므로 즉시 티남) | 수동 실행 |
| 역방향이 조용히 안 돎 | **`점검` 줄** (알림 1 · 알림 3) | 수동 실행 |
| 텔레그램이 죽음 | GitHub Actions 실패 이메일 (기본 켜짐) | 마지막 보루 |

### 7.3 점검 줄 — 상태를 만들지 않는 하트비트

GitHub Actions REST API 로 실행 이력을 조회합니다. **아무것도 저장하지 않습니다** —
이력은 GitHub 이 이미 갖고 있고, 워크플로가 읽을 뿐입니다.

```
GET /repos/{owner}/quant-notify/actions/workflows/{name}.yml/runs
    ?created=2026-09-04&status=success
```

- **누가 조회하나**: `buffer_zone` 이 **전일** 이력을, `usdkrw` 가 **지난주** 이력을
- **인증**: 워크플로 기본 제공 `GITHUB_TOKEN` (`actions: read` 권한)
- **자기 자신은 셀 수 없습니다** — 아직 실행 중이므로. 그래서 전일 기준입니다

**`2/2` 는 "2번 돌았다"이지 "2번 알림이 왔다"가 아닙니다.** 역방향은 신호가 멀면 침묵하고 그
실행도 "성공"으로 끝납니다. 점검이 보는 것은 **실행 여부**이고, 발송 여부는 알림이 왔는지로
압니다. 이 둘을 섞으면 "조용한 것이 정상인지"를 다시 구분할 수 없게 됩니다.

**조회가 실패해도 본 알림은 정상 발송합니다.** 점검 때문에 알림이 막히면 안 됩니다.

### 7.4 예외처리 원칙

- **재시도하지 않습니다** — 조회 실패는 재시도해도 같은 자리에서 실패합니다.
  "실행이 없음"과 "실행됐으나 실패"는 다르게 다룹니다
- **부분 성공을 만들지 않습니다** — SPY 는 됐는데 QQQ 가 실패하면 **전체를 실패로** 처리합니다.
  반쪽 알림은 읽는 사람이 빠진 것을 알아차리기 어렵습니다
- **보간하지 않습니다** — 값이 없으면 없다고 하고 멈춥니다
- **침묵 알림의 실패도 실패 알림을 보냅니다** — 신호가 없어서 조용한 것과 오류로 조용한 것이
  구분되어야 합니다

| **Claude 가 MA 를 직접 추론 계산** | 200일 이동평균을 LLM 추론으로 매일 계산하면 백테스트와 다른 값이 나올 수 있고 **틀려도 티가 안 납니다** |
| **Claude 가 텔레그램으로 직접 발송** | 토큰을 Anthropic 인프라에 추가로 두게 됩니다. GitHub 트리거 방식이면 불필요합니다 |
| **Claude Code Routine 을 백업 축으로** | **정시성이 측정된 바 없습니다.** cron-job.org 는 분 단위 호출이 확인됩니다 |
| **공유 DB(Firebase / Sheets)로 중복 방지** | 상태를 없애려는 목적과 모순. 애초에 중복 경로가 없습니다 (§7.1) |
| **cron 을 더 앞당기기** | 미국 서머타임 때문에 겨울(EST) 장 마감이 21:00 UTC 입니다. 여유가 줄어 겨울에 깨집니다 |
| **자동 재시도** | 데이터 검증 실패는 재시도해도 같은 자리에서 실패합니다 (§7.4) |
| **schedule 을 백업 트리거로** | 중복 발송을 부르고, 막으려면 조회 로직이 워크플로마다 붙습니다 (§6.3) |
| **알림별 데이터를 캐시로 공유** | 결합과 신선도 검증을 부릅니다. 아끼는 것은 종가 한 개입니다 (§5.4) |
| **옵션 만기일 알림** | 규칙 문서 §1.5 의 「알림 없음」 결정을 유지합니다 |
| **`state/` 를 YAML 로** | 파서가 표준 라이브러리에 없어 의존성이 하나 늘고, 워크스페이스 어느 저장소도 파이썬에서 YAML 을 읽지 않습니다. 더 큰 이유는 **타입 추론**입니다 — 따옴표 없는 `NO`·`ON` 이 boolean 으로 파싱되는데 둘 다 실재하는 티커이고, 들여쓰기가 밀려 값이 옆 종목에 붙어도 **파일은 여전히 유효한 YAML** 이라 파서가 통과시킵니다. 값이 조용히 틀리는 것이 이 저장소가 가장 피하려는 실패입니다 |
| **`state/` 를 DB(Firebase · SQLite 등)로 대체** | **매일 갱신이 없어 DB 가 풀 문제가 없습니다.** 사람이 매매할 때만 고치는 YAML 을 하루 한 번 읽을 뿐이라 동시 쓰기도 트랜잭션도 없습니다. SDK 의존성과 자격증명이 늘 뿐이고, 그것은 §3.1·§3.3 에서 방금 걷어낸 것입니다 |
