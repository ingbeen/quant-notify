## 1. ECOS — 원달러 환율 (2026-09-05 실측)

### 1.1 확정된 코드

| 항목 | 값 | 라벨 |
| --- | --- | --- |
| 통계표 | **`731Y003`** | 3.1.1.3. 원화의 대미달러, 원화의 대위안/대엔 환율 |
| 항목 | **`0000003`** | **원/달러(종가 15:30)** |
| 주기 | `D` | 일별 |

### 1.2 왜 이 코드인가 — 비슷한 계열이 넷 있습니다

**여기가 함정입니다.** ECOS 에는 「원달러」로 읽히는 계열이 여러 개이고, **어느 것을 골라도
조회는 성공합니다.** 다른 계열을 고르면 알림 숫자가 조용히 틀립니다.

| 통계표 / 항목 | 라벨 | 2026-08-26 값 |
| --- | --- | --- |
| `731Y001` / `0000001` | 원/미국달러(**매매기준율**) | 1,383.1 |
| **`731Y003` / `0000003`** | **원/달러(종가 15:30)** | **1,384.8** |
| `731Y003` / `0000013` | 원/달러(종가) | 미확인 |
| `731Y003` / `0000002` · `0000004` · `0000005` | 시가 · 저가 · 고가 | — |

원달러 규칙(`docs/DESIGN.md` §4.3)이 **정규장 종가**를 쓰고, 15:30 은 정규장 마감 시각입니다.
**매매기준율은 전일 은행간 거래의 가중평균이라 다른 값**입니다.

### 1.3 계산 경로 검증 — 정본과 대조했습니다

verify-lab 원달러 문서의 2026-08-26 기준 실측값(지금은 `docs/조사/원달러_조달.md` §10.3)과 맞춰봤습니다.

| 항목 | 이 저장소 | 정본 문서 | 판정 |
| --- | ---: | ---: | --- |
| 현재값 | 1,384.8 | 1,384.80 | **일치** |
| 1년 평균 | 1,462 | 1,462 | **일치** |
| 1년 평균대비 | **-5.3%** | -5.3% | **일치** |
| 3년 평균 | 1,404 | 1,404 | **일치** |
| 3년 평균대비 | **-1.3%** | -1.3% | **일치** |
| 5년 평균 | 1,352 | 1,351 | 1원 차 |
| 5년 평균대비 | **+2.5%** | +2.5% | **일치** |

**알림에 나가는 숫자(평균대비)가 세 창 모두 소수 1자리까지 같습니다.**

`731Y001/0000001`(매매기준율)로 같은 계산을 하면 현재값이 **1,383.1** 이고 1년 평균대비가
**-5.4%** 로 어긋납니다. 조회는 똑같이 성공하므로 **대조하지 않으면 알아차릴 수 없습니다.**

### 1.4 창 경계는 양끝을 포함합니다

거래일 수가 1개씩 어긋나 확인한 결과, 같은 문서의 검산이 **"2025-08-26 ~ 2026-08-26, 246 거래일"**
로 **시작일을 포함**합니다. 시작일을 빼면 245일이 되고 5년 평균이 1원 어긋납니다.

**창을 자를 때 `start <= 날짜 <= end` 로 양끝을 포함합니다.**

### 1.5 응답 시간

| 조회 | 행 수 | 시간 |
| --- | ---: | ---: |
| 10년치 (`2016-09-07 ~ 2026-09-05`) | 2,460 | **0.76초** |
| 11년치 (`2015-01-02 ~ 2026-08-26`) | 2,861 | 1초 미만 |

워크플로 제한 시간에 걸릴 여지가 없습니다.

### 1.6 인증키를 환경 변수에 올리지 않습니다

`.env` 는 `dotenv_values` 로 값만 읽고 `os.environ` 에 올리지 않습니다 — 올리면 이후
실행되는 모든 하위 프로세스가 키를 상속받습니다. 인증키가 URL 경로에 들어가 마스킹하는 이유는
`docs/DESIGN.md` §3.4 에 있습니다.

### 1.7 인증키를 «읽는» 길은 하나여야 합니다

**설정값을 읽는 함수는 `utils/config.py` 의 `read_config` 하나뿐입니다.** 환경 변수를
먼저 보고 없으면 `.env` 를 봅니다.

**두 길을 두었다가 워크플로에서만 깨진 적이 있습니다.** ECOS 인증키만 `.env` 를 직접 여는
함수를 쓰고 있었는데, **로컬에는 그 파일이 있어 테스트도 dry-run 도 전부 통과했습니다.**
GitHub Actions 에는 `.env` 가 아예 없고 시크릿이 환경 변수로 들어오므로 거기서만 드러났습니다.

> 🔴 **그래서 「자격증명 파일을 직접 여는」 함수를 만들지 않습니다.** 이름이 그럴듯한 함수가 남아
> 있으면 다시 쓰여 같은 장애가 재발합니다 — 호출처를 줄이는 것으로는 부족하고, 없애야 닫힙니다.

## 2. yfinance — 미국 상장 종목 (2026-09-05 실측)

### 2.1 조정 종가를 씁니다

**이것을 틀리면 이동평균이 어긋납니다.** QQQ 로 실측한 차이입니다.

| 계산 | SMA200 |
| --- | ---: |
| 조정 종가 (`auto_adjust=True`) | **656.78** |
| 원시 종가 (`auto_adjust=False`) | 657.71 |
| 차이 | **0.93 (약 0.14%)** |

근접도를 **소수 둘째 자리**까지 내므로 이 차이는 화면에 그대로 보입니다.

**근거**: quant 의 `src/qbt/utils/stock_downloader.py` 가 `Ticker.history()` 를 쓰고, 그 기본값이
`auto_adjust=True` 입니다. quant 문서 `docs/research/QQQ_지연진입_연구.md` 도
*"사후 데이터: **수정주가(yfinance adjusted)** 기준"* 이라고 적었습니다.

**기본값에 기대지 않고 `auto_adjust=True` 를 명시합니다.** 라이브러리 판이 바뀌면 기본값도 바뀝니다.

### 2.2 응답 형태

| 항목 | 값 |
| --- | --- |
| 판 | yfinance 0.2.66 (측정 당시) |
| `period="1y"` 거래일 | **252** (200일 이동평균에 52일 여유) |
| `auto_adjust=True` | `Close` 가 이미 조정값 |
| `auto_adjust=False` | `Adj Close` 가 따로 |

**두 호출의 응답 형태가 다릅니다** (2026-09-07 실측).

| | `yf.download` | `Ticker.history` |
| --- | --- | --- |
| 컬럼 | **두 겹(MultiIndex)** — 종목 하나만 받아도 `("Close", "QQQ")` | **한 겹** — `Close` |
| 인덱스 | tz 없음 (일봉은 `ignore_tz=True` 가 기본) | **거래소 현지 tz** — `America/New_York` · `Asia/Seoul` |
| 실패한 종목 | 예외를 **삼키고** 빈 프레임 | 예외를 그대로 올림 (`raise_errors=True`) |

**코드는 `Ticker.history` 를 씁니다.** 마지막 줄이 이유이며 §2.4 에 있습니다.

**값은 같습니다** — `period="1y"` 로 두 경로를 대조했습니다 (2026-09-07).

| 티커 | download 행 | history 행 | 종가 최대차 | SMA200 차이 |
| --- | ---: | ---: | ---: | ---: |
| QQQ | 252 | 252 | 0.0000610 | 0.0000043 |
| SPY | 252 | 252 | 0.0000000 | 0.0000000 |
| 069500.KS | 243 | 243 | 0.0156250 | 0.0002930 |

행 수가 같아 **SMA200 계산이 깨지지 않습니다.** 남는 차이는 `download` 가 concat 과정에서
float32 폭을 거치는 데서 오며, 크기가 float32 epsilon 과 맞습니다 (QQQ 656 에서 0.00006,
KODEX 92,961 에서 0.0078). 근접도는 소수 둘째 자리까지 내므로(§2.1) 그보다 다섯 자리 아래입니다.
QQQ SMA200 은 양쪽 모두 **656.782** 로 §2.1 에 기록된 값과 같습니다.

### 2.3 조회 시간

SPY · QQQ · GLD · TLT 네 종목을 한 번에 받아 **0.89초**, 각 252행입니다.
`Ticker.history` 로 **종목별 순차** 조회하면 같은 네 종목이 **1.59초** 입니다 (2026-09-07 실측).
워크플로 제한 시간(10분)과 무관한 크기이므로, 예외를 살리는 대가로 치를 만합니다.

### 2.4 조회 실패는 원인을 담아야 합니다 (2026-09-07 실측)

**GitHub Actions 러너에서 조회 한도(429)에 걸렸습니다.** (당시 있던 한국 종목 알림의 실행입니다)

| 항목 | 값 |
| --- | --- |
| 실패 run | `34087068444` (05:30 UTC = 14:30 KST) |
| 실패까지 | 스텝 시작 05:30:35 → 실패 05:30:40. **5초** |
| Actions 로그 | `['069500.KS']: YFRateLimitError('Too Many Requests. Rate limited. Try after a while.')` |
| 텔레그램 알림 | `ValueError: 시세를 받지 못했습니다: 069500.KS. 조회를 다시 실행하세요.` |
| 같은 시각 로컬 | **통과** |
| 빈도 | 실행 이력 14건 중 데이터 조회 실패 1건. **표본이 이틀치라 작습니다** |

**원인이 알림에서 사라졌습니다.** `yf.download` 는 종목별로 `Ticker.history()` 를 부르고
**예외를 통째로 삼켜** 빈 프레임을 넣습니다 (`multi.py:289-293`). 실제 예외는 `shared._ERRORS`
에만 남습니다. 그래서 조회 코드의 `except` 가 한 번도 걸리지 않고 「빈 프레임」 가지로 떨어져,
429 라는 사실이 빠진 문구가 나갔습니다.

**왜 문제인가**: 조회 한도(`YFRateLimitError`)와 종목 소멸(`YFPricesMissingError`)은 대응이
다릅니다. 앞은 다시 돌리면 되고 뒤는 종목을 고쳐야 합니다. 문구로 갈리지 않으면 Actions
로그를 열어야 알 수 있습니다. 그래서 `Ticker.history(raise_errors=True)` 로 바꾸고
**예외 클래스명과 메시지를 문구에 싣습니다.**

**yfinance 는 이미 자체 재시도를 합니다.** 429 를 받으면 쿠키 전략을 `basic` ↔ `csrf` 로 바꿔
크럼을 다시 받고 한 번 더 보냅니다 (`data.py:420-432`). 그래도 429 면 예외를 냅니다.
**즉시 재시도는 이미 해봤고 통하지 않습니다** — 재시도를 넣는다면 지연 재시도여야 하고,
그것이 통한다는 실측은 아직 없습니다.

### 2.5 일봉 종가가 «비어 있는 채로» 오는 일이 있습니다 (2026-09-09 실측)

거래일 행은 오는데 **`Close` 만 `NaN`** 인 상태를 관측했습니다. 미국 4종목 전부입니다.

| 조회 시각 (KST) | SPY | QQQ | GLD | TLT |
| --- | --- | --- | --- | --- |
| 09:00 | NaN | NaN | NaN | NaN |
| 09:28 | NaN | NaN | NaN | NaN |
| 10:40 | NaN | NaN | NaN | NaN |
| 10:47 | 765.96 | 718.36 | 399.72 | 82.20 |

**약 1시간 40분 이상 지속된 뒤 스스로 채워졌습니다.** 영구 결손이 아니라 간헐적
결손이며, 같은 시각 한국 종목은 정상이었습니다. 조회 형태(`period` 1y·6mo·1mo·5d, `start`/`end`)와
무관하게 같았고 복구도 동시에 됐습니다.

**이것이 위험한 이유는 조용하기 때문입니다.** 빈 값을 떨구면 그 행은 **자취 없이 사라지고**,
계열의 끝을 위치로 집으면 하루 전 종가가 잡힙니다. 예외도 로그도 없고 알림 형태로는 정상으로
보입니다. 그래서 판정이 읽는 종가는 날짜로 집고, 없으면 멈춥니다 (`docs/DESIGN.md` §7.4).

**그날 07:30 알림은 정상이었습니다.** 화면의 근접도에서 09-08 종가를 역산하면
765.98 · 718.34 · 399.73 · 82.20 이 나오는데, 10:47 에 받은 실측값과 소수 둘째 자리까지
같습니다. 결손 창이 발송 시각을 비켜간 것이지 코드가 막아준 것이 아닙니다.

참고로 **이동평균 창이 하루 밀리는 것만으로는 근접도가 크게 흔들리지 않습니다** —
같은 종가에 창만 1일 밀어 재면 SPY +0.0841 · QQQ +0.0980 · GLD +0.0414 · TLT -0.0206 (%p)
입니다. 위 역산이 신뢰할 만한 이유이자, 창 전체의 거래일 공백까지 검증하지 않기로 한 근거입니다.

**장중에 받은 일봉에는 그날의 미확정 봉이 끝에 섞여 옵니다** (2026-09-07 한국 장중 관측).
이동평균 창을 판정 날짜에서 끊지 않으면 target 뒤 미확정 봉이 섞입니다 — target 종가 104.0
고정으로 재면 SMA 100.0200 / 근접도 +3.98% 가 SMA 100.1200 / 근접도 **+3.88%** 가 됩니다(0.10%p).
판정 날짜 자체가 진행 중인 세션이면 그 날의 값이 종가처럼 보이므로, 그때는 멈춥니다.

## 3. exchange-calendars — 휴장 판정

### 3.1 달력이 다루는 범위는 실행 시점 기준입니다 (2026-10-07 확인)

범위는 라이브러리 판이 아니라 **`get_calendar` 를 부르는 날 기준 20년 전 ~ 1년 뒤**로 정해져 날마다
움직입니다(그날 `2006-10-09 ~ 2027-10-07`). 그래서 판정하는 어제 날짜는 늘 범위 안입니다.
범위 밖 날짜는 라이브러리가 `DateOutOfBounds`(`ValueError` 하위형)를 직접 냅니다.

**판이 낡아서 생기는 진짜 위험은 새로 지정된 임시공휴일을 모르는 것**입니다. 그날은 거래일로
판정돼 시세를 받고, 그날 종가가 없어 날짜 가드가 실패 알림으로 드러냅니다.

### 3.2 달력은 한 번 만들면 캐시됩니다 (2026-09-11 실측)

`xcals.get_calendar` 는 같은 거래소를 다시 부르면 만들어 둔 것을 돌려줍니다 — 처음 만들 때
0.114초, 같은 실행 안에서 다시 부르면 0.000초입니다. **판정 경로에 달력 조회를 더해도 비용이
늘지 않습니다.**

### 3.3 알려진 경고

`exchange_calendars` 4.13.2 가 NumPy timedelta 관련 `DeprecationWarning` 을 냅니다.
**라이브러리 내부 문제이고 판정 결과에는 영향이 없습니다.** `pytest.ini` 가
`DeprecationWarning` 을 표시만 하고 실패시키지 않아 검증은 통과합니다.

## 4. 스케줄 — 발화 정시성과 겨울 여유

### 4.1 cron-job.org 발화 정시성 (2026-09-07 실측)

정시 대비 **+18 ~ 28초**입니다 (07:30:18 · 12:00:28 · 14:30:18). 분 단위 정시성이 확인됐습니다.

### 4.2 겨울 발송 여유 — 가드가 오탐할 수 있는 자리 (미측정)

§2.5 의 날짜 가드는 target 날짜의 종가가 없으면 알림을 실패시킵니다. **정상인데 실패로
판정하는 경우**가 이 시스템의 실질적 위험이고, 그 여지가 가장 큰 때가 겨울입니다.

| 시기 | 미국 마감 (KST) | `buffer_zone` 07:30 여유 |
| --- | --- | ---: |
| 서머타임 (EDT) | 05:00 | 2시간 30분 |
| 겨울 (EST) | 06:00 | **1시간 30분** |

§2.5 의 결손이 1시간 40분 이상 이어졌으므로, **같은 폭의 결손이 겨울 마감 직후에 나면
실행이 그 창 안에 들어갑니다.** 서머타임에는 여유가 그만큼 더 있습니다.

**겨울 여유를 처음 겪는 것은 2026-11-03 (화) 알림입니다.** 서머타임은 11-01 (일)에 끝나지만
일·월은 버퍼존 알림이 없습니다 — 10-30 (금) 마감은 아직 EDT 라 10-31 (토) 05:00 KST 이고,
첫 EST 마감인 11-02 (월) 16:00 이 11-03 (화) 06:00 KST 입니다.

**「1시간 40분」은 하한선입니다.** §2.5 의 관측에서 07:30 에 멀쩡하던 값이 09:00 에는 비어
있었고 10:47 에 채워졌습니다. 결손의 시작이 마감 직후로 고정된 것이 아니므로 **여유를 몇 분
늘리는 방식으로는 안전을 장담할 수 없습니다.** 지켜보는 방법과 대응은 `docs/DESIGN.md` §9 에 있습니다.

**폴백 데이터 소스는 두지 않았습니다.** 이유는 셋입니다. ① 이동평균은 조정 종가라야
백테스트와 맞는데(§2.1) 다른 소스는 조정 기준이 다릅니다. ② 두 소스가 어긋날 때
무엇이 옳은지를 시스템이 **조용히** 판정하게 됩니다. ③ 결손 빈도를 아직 재지 못했습니다 —
가드가 먼저 그 실측을 쌓아야 폴백이 필요한지 알 수 있습니다.

## 5. GitHub Actions REST API — 실행 이력 조회 (2026-09-11 실측)

점검 줄(`docs/DESIGN.md` §7.3)이 읽는 외부 소스입니다. 시세가 아니라 **이 시스템 자신의
실행 기록**이지만, 조회 규격을 모르면 값이 조용히 틀린다는 점은 앞의 절들과 같습니다.
측정은 당시 있던 다른 워크플로(`reverse_rank_us` · `reverse_rank_kr`)로 했고, 결론은 워크플로와 무관합니다.

### 5.1 `created` 필터는 «UTC» 기준입니다

`created=<날짜>` 는 UTC 날짜로 해석됩니다. 한국시간 날짜를 그대로 넘기면 어긋납니다.

```
GET .../workflows/reverse_rank_us.yml/runs?created=2026-09-10&status=success
  → {"total_count": 1, "runs": ["2026-09-10T22:30:21Z"]}
```

돌아온 실행의 발화 시각은 **22:30Z = 한국시간 09-11 07:30** 입니다. 「09-10」으로 물었는데
한국시간 09-11 의 실행이 온 것입니다.

| 워크플로 | 발화 (KST) | 발화 (UTC) | KST 날짜와 |
| --- | --- | --- | --- |
| `buffer_zone` | 07:30 | **전날 22:30** | **하루 밀림** |
| `usdkrw` | 월 07:30 | **일 22:30** | **하루 밀림** |

### 5.2 범위 구문이 동작합니다 — KST 하루를 이렇게 묻습니다

`created` 는 `시작..끝` 형태를 받습니다. 한국시간 하루는 **전날 15:00:00Z ~ 당일 14:59:59Z** 입니다.

```
created=2026-09-09T15:00:00Z..2026-09-10T14:59:59Z     # = KST 2026-09-10 하루
  → reverse_rank_us : 2026-09-09T22:30:22Z              1건 (KST 09-10 07:30)
  → reverse_rank_kr : 09-10T03:00:29Z, 09-10T05:30:21Z  2건
```

**아침 실행과 낮 실행이 같은 구간에 함께 들어옵니다.** 워크플로마다 오프셋 표를
두지 않아도 되는 이유입니다. 한국은 서머타임이 없어 구간 폭이 언제나 같습니다.

### 5.3 `requests` 가 이 값을 그대로 싣습니다

파이썬에서 `params` 로 넘길 때 인코딩이 깨지지 않는지 확인했습니다.

```
https://api.github.com/repos/ingbeen/quant-notify/actions/workflows/reverse_rank_us.yml/runs
  ?created=2026-09-09T15%3A00%3A00Z..2026-09-10T14%3A59%3A59Z&status=success
  → {"total_count": 1, "runs": ["2026-09-09T22:30:22Z"]}
```

**`:` 만 `%3A` 로 바뀌고 `..` 은 보존되며, GitHub 이 그대로 처리합니다.**

## 6. MA 근접도 표시 범위 (2026-09-23 실측)

`docs/DESIGN.md` §4.3 의 「두 선 사이에서만 수치로 낸다」를 정할 때 잰 값입니다.

**2016-01-04 ~ 2026-08-21 의 이벤트를 셌습니다.** 「전환」은 수치와 문구가 서로 바뀐 횟수입니다.
