## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

`state/reverse_rank.toml` 의 20위 등락률은 사용자가 verify-lab 에서 계산해 손으로 적는 값이다. 정본 `reference/역방향_매매_규칙.md` §1.5 의 전 기간 실측이 **「20위 값이 바뀌는 날은 반드시 신호일」**(KODEX 186/186 · QQQ 182/182, 값만 바뀐 날 0일)을 확인했으므로, 갱신 시점은 신호일이다.

그런데 **지금은 그 연결이 코드에 없다.** 신호 알림은 신호만 알리고, 사용자가 「이 알림이 왔으니 순위를 다시 매겨야 한다」를 기억해야 한다. 그리고 한국은 장중 판정(~14:08 값, 종가 단일가 포함 마지막 31분은 영구히 오지 않음 — DESIGN §9)이라 **종가 기준으로는 신호인데 장중에는 미달인 날**이 알림 없이 지나간다.

#### 단순 조건 「창 안에 20위 도달한 날이 있나」만으로는 경고가 꺼지지 않는다

어떤 날의 등락률 `r` 이 20위 안에 들어오면 기존 20위가 21위로 밀려 **새 20위 = min(r, 기존 19위)** 가 된다. 두 경우 다 `r >= 새 20위` 다 — `r` 이 기존 19위 이상이면 새 20위가 기존 19위라 `r` 이 더 크고, 그 사이면 새 20위가 `r` 자신이라 동률이다. 정본 §1.5 가 **"도달하거나 넘으면 신호(동률 포함)"** 이므로 동률도 도달이다.

**즉 상위 20위에 든 날은 영구히 「도달」이다.** 갱신해도 조건이 계속 참이므로, 고정 창만 보면 신호 1회당 창 길이만큼 매일 경고가 뜬다. 연 6~7회면 1년의 절반 남짓이고, 이는 DESIGN §4.5 가 경고한 상태다 — *"흔해져서 정작 사건일 때 눈에 걸리지 않습니다."*

**해법은 `data_to` 를 함께 견주는 것이다.** `data_to` 는 그 20위 값을 매길 때 넣은 마지막 날이므로, 그보다 **뒤**의 날이 곧 「아직 반영되지 않은 날」이다. 사용자가 재계산해 `data_to` 를 올려 커밋하면 그 날이 창에서 빠져 **경고가 상태 없이 스스로 꺼진다.**

#### 창 길이를 한 달로 고정하지 않는다

`data_to` 가 이미 시작점을 정하므로 한 달은 덧붙은 상한이다. 상한은 받아 둔 시세(`DEFAULT_PERIOD = "1y"`)가 자연히 정한다.

**1년을 넘긴 `data_to` 에 경고를 붙이지 않는다.** QQQ 는 정본 §1.5 실측으로 **최근 5년간 20위 값이 2회만** 바뀌었다 — `data_to` 가 1년보다 오래된 것이 QQQ 에서는 정상이다. 경고를 붙이면 거짓 경고가 영구히 켜진다. 매일 도는 일일 축이 있으므로, 신호는 발생 다음 거래일에 잡히고 1년 상한은 실질적으로 무해하다. **1년을 넘는 공백을 만들 수 있는 것은 1년 이상의 알림 장애뿐이고, 그것은 점검 줄이 드러낸다**(DESIGN §7.3).

#### `as_of` 를 없애는 이유

`as_of`(값을 계산한 날)와 `data_to`(계산에 넣은 마지막 시세 날)는 **다른 값인데 현재 파일에서 같다.** 판정이 물어야 하는 것은 「이 날이 줄 세우기에 들어갔나」이므로 답은 `data_to` 하나다. `as_of` 를 기준으로 비교하면 `as_of > data_to` 인 경우(예: 9/1 에 앉아 8/26 까지로 계산) **그 사이 날의 신호를 「이미 반영됨」으로 오판해 놓친다.**

두 날짜를 남겨 두면 다음 사람이 어느 쪽과 비교해야 하는지 매번 판별해야 하고, 이 작업 뒤에도 `as_of` 는 호출 0건으로 남는다. 전역 `~/.claude/rules/python.md` 「미사용 판정」 표의 **「필요 없어서」 → 지운다** 에 해당한다.

> 정본 §1.5 의 「소비하는 쪽에 넘기는 것」 표는 "그 값이 정해진 기준일·데이터 기간"을 넘긴다고 적었다. **`data_to` 가 기준일 역할을 겸하므로 규격 이탈이 아니다** — 정본은 보관 매체와 필드 구성을 정하지 않는다("보관 매체는 이 문서가 정하지 않습니다").

## 6) 단계별 계획(Phases)

### Phase 0 — 판정 규칙을 테스트로 먼저 고정(레드)

판정이 「조용히 틀리는」 종류라 테스트를 먼저 세운다. `tests/test_rank_staleness.py` 에 고정한다.

**판정을 두 순수 함수로 가른다.** 창 경계와 도달 판정을 나누면 달력·시세 없이 둘 다 테스트된다 — 창 가드를 `cli.py` 에 두면 그 가드만 모킹 없이는 검증할 수 없다.

| 함수 | 받는 것 | 내는 것 |
| --- | --- | --- |
| `unreflected_window` | `data_to` · 마지막 확정 종가일 · 등락률을 낼 수 있는 첫 거래일 | 창 `(시작, 끝)` 또는 `None`(검사할 날 없음) |
| `unreflected_days` | 날짜별 등락률 · `thresholds` · `data_to` | 반영되지 않은 도달일 목록 |

**작업 내용**:

- [x] `unreflected_days` — 20위에 도달했고 `data_to` 보다 뒤인 날 → **갱신 필요로 잡힌다**
- [x] `unreflected_days` — 20위에 도달했지만 `data_to` 이하인 날 → **잡히지 않는다** (이미 반영된 날)
- [x] `unreflected_days` — 동률(`rate == rate_20th`)도 도달로 센다 — 정본 §1.5 「도달하거나 넘으면」
- [x] `unreflected_days` — **회귀: 갱신하면 꺼진다.** 같은 등락률에 더 극단적인 새 20위와 올라간 `data_to` 를 주면 잡히지 않는다. **이 테스트가 Context 의 「영구히 켜지는」 결함을 막는다**
- [x] `unreflected_days` — 폭등·폭락을 **따로** 판정한다 (방향별 독립 순위 — 정본 §1.5)
